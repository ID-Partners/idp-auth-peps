idp-auth-peps · an overview

One decision, three enforcement points

Policy Enforcement Points that speak OpenID AuthZEN 1.0 to a Policy Decision Point and enforce the answer at whatever sits in front of your traffic: a Kong plugin, an Envoy ext_authz service, and a Node SDK. They share one engine, so an agent gets the same answer, and the same resolvable challenge on a deny, whichever one said no.

The problem

An AI agent calling a tool is one agent, acting for one human, touching one resource, right now. Whether that is allowed depends on all three, and it belongs in policy, not in tool code. AuthZEN gives a PEP a standard way to ask a PDP that question. This repository is the enforcement side: it never decides, it asks, and it makes sure the asking is done the same way everywhere.

The interesting part is the deny. A flat 403 tells an agent nothing it can act on. So when the policy says how a deny could be resolved, every PEP here renders that the same three ways: an HTTP WWW-Authenticate header, a JSON body, and an MCP JSON-RPC error's data.authz_challenge.

gateways/kongKong plugin

Native Lua for claims, REST mapping, challenges and PDP discovery. Delegates DPoP verification and COAZ tool-call checks to the engine: a plugin has no JOSE verifier and no CEL.

gateways/envoy · core/Envoy family

agentgateway, Istio and plain Envoy attach ext_authz to coaz-pep, the Go engine. No gateway code at all; per-route knobs travel as context_extensions.

sdk/nodeNode SDK

In-process: an AuthZEN client, Express middleware, an MCP guard. Evaluates a deliberately narrow CEL subset itself and delegates the rest, exactly as Kong does.

The decision contract

Same words in a header, a body and an MCP error

Every PEP sends the PDP the same shape: the agent is the subject, the human it acts for is subject.properties.on_behalf_of, and the context carries what the policy needs to reason about the delegation: the user token's scope, acr, any RFC 9396 authorization_details, and the token audience.

The context also carries what the PEP found rather than decided: the resource's metadata document, the endpoint hit and, per route, the raw token. That is the next section.

For MCP the PEP does not authorise “POST /mcp”. It reads the JSON-RPC body, finds the tool, and authorises that call under the AuthZEN MCP profile (COAZ): the server's tools/list declares, per tool, how to map arguments and claims into an AuthZEN request. Deny and error semantics are JSON-RPC errors over HTTP 200, as the profile requires.

Finding the PDP

Who decides for this resource, and who gets to say so

Every PEP used to be told where the PDP is and assumed the AuthZEN paths under it. Discovery replaces both assumptions with metadata: the resource names its PDP, the PDP publishes its endpoints. No standard names a PDP from a protected resource (not RFC 9728, not AuthZEN 1.0, not the MCP profile, not Federation 1.0), so this repository mints one parameter and uses it everywhere:

"authzen_policy_decision_points": ["https://pdp.example"]

An array of PDP identifiers, first preferred, and the same bytes whether it sits in an RFC 9728 document or under metadata.oauth_resource in a federation Entity Statement. That sameness is the point, because the two places differ in who vouches for them.

ModeWhat the PEP readsFalls back to

authzenthe static PDP's /.well-known/authzen-configurationthe AuthZEN default paths
resourcethe resource's RFC 9728 document, then the named PDP's metadatathe static PDP
federationthe resource's resolved oauth_resource metadata, then the named PDP's metadatathe static PDP, never the resource's own document

Federation resolution lives only in the Go engine. Kong and the Node SDK implement the resource and authzen modes natively and get federation by delegating.

What the PEP forwards, and what it does not decide

The gateway carries the requirement. The PDP enforces it.

A resource's metadata says more than who decides for it. RFC 9728 gives it scopes_supported, dpop_bound_access_tokens_required and friends; a federation can constrain any of them and add its own. A resource that wants MFA for everything it serves has somewhere to say so.

The design choice is what the PEP does with that: nothing but carry it. Every PDP call carries the resource's document verbatim as context.resource_metadata, tagged with whether it is a self-assertion or the federation-resolved one; the endpoint hit as context.request; and, when the route allows, the raw token as context.access_token. The PEP does not compare a token's scope or acr to anything. It does not know the names of those members.

Why offload itWhat it buys
Policy in one placeA gateway comparing strings is policy in two places, and the gateway's copy is the dumber one: it cannot see risk, consent history, velocity or device posture. The PDP weighs a resource's requirement against all of that.
Changeable without a deployThe resource publishes what it requires; the PDP enforces it. Neither needs the gateway redeployed when it changes.
The deny stays resolvableA PDP that knows the requirement can say what would satisfy it, and the PEP renders that as a challenge. A gateway enforcing the same thing could only 403.
The PDP examines the token itselfWith the raw token forwarded it can verify the signature, read cnf, score the client. Off by default per route: whether a PDP is trusted with the token is a separate choice from whether it is trusted with the decision.

In federation mode the forwarded document is the resolved one, so an anchor that sets acr_values_required to MFA has set it for every PDP that reads it, and a member cannot lower it by editing its own well-known. In the demo, the same PDP with the same policy and the same token permits through the resource-mode PEP and denies through the federation-mode one, and its reason names which document it was reading.

Layers

A generic PDP first, the resource's after

One PDP per resource is not the only shape. An estate has questions every endpoint shares — is this client in good standing, is this token sender-constrained, does the risk score allow anything at all — and a PDP that answers them knows nothing about any particular resource. It should not have to.

So a route names an ordered list of layers, and the PEP asks each in turn with the same request and the same forwarded context. Every layer must permit. The first that does not is the answer, advice and all, and the rest are not asked: a generic layer is a gate in front of a specific one. A PDP error in any layer fails closed unless that layer was told otherwise. Two layers that resolve to the same PDP are one call.

LayerWhat it is
staticThe configured PDP, regardless of what discovery finds. The slot for an estate-wide PDP.
resourceWhatever discovery resolves for the route's resource: federation, then RFC 9728, then static. The default, and the whole of today's behaviour when it is the only layer.
a PDP identifierAn explicit PDP, its metadata read like any other. From the service's own configuration it is trusted; from a route's configuration it must be on the allowlist, like anything else that arrives over the check API.

In the demo an estate PDP denies a client on its watch list and permits everything else. Put first in pdp_layers, it stops a risky client before Bank A's PDP ever hears about the request.

Failing open, deliberately

A PDP that cannot be reached is an outage, and the answer to an outage is deny. That is the default everywhere. But an estate PDP that adds a risk score in front of the PDP that owns the resource is advice worth having and not worth an outage, and whether that is true is a judgement about that layer. So a layer may say for itself what happens when it fails, as a suffix on its entry (https://estate.example fail-open), and a PEP may set the default for layers that say nothing (PDP_FAIL_MODE, a route's fail_mode, Kong's fail_mode, the SDK's failMode). The layer's own word wins.

Fail-open covers availability and nothing else: unreachable, erroring, unresolvable, or asked for a batch it cannot take. A fail-open layer that fails is skipped and the rest decide; if every layer was skipped the request is permitted, and the permit is marked. X-PDP-Fail-Open names what was skipped, the SDK's verdict carries failedOpen, and the PEP logs it. A deny is a decision, never skipped. A refusal, an off-list PDP or a chain that does not validate, is the PEP's own rule, and an outage does not lift it.

The rules that never relax

Fail closed where it matters, degrade everywhere else

  • A URL outside an allowlist, or a chain that fails validation, is a 503. It never falls through to a weaker source. Everything else degrades: a stale cache, then the operator's own static PDP, and only when nothing is left is the request denied.
  • A discovered PDP never receives the static API key. The key is bound to the configured PDP alone.
  • A batch is never sent to a guessed path. A boxcar mapping needs the PDP to advertise access_evaluations_endpoint.
  • Metadata is cached per identifier with stale-while-failing, refresh throttling and negative caching, so a metadata outage is not an authorisation outage and a down resource does not put a fetch in every request's path.
  • Allowlists are re-applied on every call, not only when a document is fetched: a cache is shared, a policy is per route. Which resources may be looked up is one allowlist; which hosts a chain may climb through is another.
The gateway as the resource's federation face

The PEP holds a key. The controller holds the policy.

A federated resource publishes two things: a signed entity configuration a trust controller fetches to onboard it, and its RFC 9728 metadata. The gateway is the resource's public face, so it is the natural place for both. coaz-pep holds the key and serves both documents; the Kong plugin relays them from it; the Node SDK's FederationEntity signs and serves its own.

The entity configuration is deliberately minimal: the public key, authority_hints, and the entity type. No policy lives on the PEP. Which PDP decides for the resource, which scopes it uses, which acr it requires, all of that is the controller's, in the subordinate statement it issues, and changing it there changes what every consumer sees on its next refresh without touching a gateway.

The PEP then republishes what the federation resolved for it as the resource's RFC 9728 document, signed_metadata included, so a plain RFC 9728 consumer reads the federation's word without knowing a federation is behind it. Until the controller has onboarded the entity the document is self-asserted, says only which PDP the PEP is configured with, and says so in a header.

Deliberately not here
  • A PDP. These are enforcement points. In our deployments the PDP is Ping Authorize behind its AuthZEN adapter; any conformant PDP works.
  • A general path-to-resource mapper in the SDK. Guessing a resource from a URL is how a PEP authorises the wrong thing. You write the mapping.
  • Trust Marks, the resolve endpoint, historical keys, client auth at federation endpoints. Chain resolution and metadata policy answer the question at hand.
  • An AuthZEN entity type for the PDP. No spec defines one yet; the seam is there for when one does.
